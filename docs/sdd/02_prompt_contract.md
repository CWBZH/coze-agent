## 1. 商品 JSON 注入格式

### 1.1 标准格式

商品 JSON 采用以下结构（字段顺序固定）：

```json
{
  "goods_id": "946901558797",
  "goods_name": "净爽止汗喷雾保湿除臭净味爽身清新舒爽温和腋下止汗香体20ml",
  "category": "止汗喷雾",
  "brand": "伊思棠",
  "price": "19.9元",
  "sku_summary": "一瓶20ml",
  "sku_options": ["一瓶", "2瓶", "3瓶"],
  "fragrance": "茉莉、栀子、纯净微风",
  "effect": ["止汗", "除臭", "清爽"],
  "ingredients": "",
  "usage_method": "",
  "usage_duration": "",
  "suitable_age": "",
  "skin_type": "",
  "foaming": "",
  "shelf_life": "",
  "warnings": [],
  "accessories": []
}
```

### 1.2 字段说明

| 字段 | 类型 | 含义 | 空值处理 |
|------|------|------|----------|
| `goods_id` | string | 商品 ID | 必须存在 |
| `goods_name` | string | 商品名称 | 必须存在 |
| `category` | string | 主类目 | 空时回复"我不确定这个商品的类目" |
| `brand` | string | 品牌 | 空时回复"我不确定这个品牌" |
| `price` | string | 商品价格 | 空时回复"请以商品页面实际价格为准" |
| `sku_summary` | string | 默认规格 | 空时回复"我不确定默认规格" |
| `sku_options` | array | 可选规格列表 | 空数组时回复"我不确定有哪些规格" |
| `fragrance` | string | 香味 | 空时回复"我不确定香味信息" |
| `effect` | array | 功效卖点 | 空数组时回复"我不确定具体功效" |
| `ingredients` | string | 成分/材质 | 空时回复"我不确定成分信息" |
| `usage_method` | string | 使用方法 | 空时回复"我不确定具体使用方法" |
| `usage_duration` | string | 使用时长 | 空时回复"我不确定能用多久" |
| `suitable_age` | string | 适用年龄/人群 | 空时回复"我不确定适用人群" |
| `skin_type` | string | 适用肤质 | 空时回复"我不确定适用肤质" |
| `foaming` | string | 起泡情况 | 空时回复"我不确定起泡情况" |
| `shelf_life` | string | 保质期 | 空时回复"我不确定保质期" |
| `warnings` | array | 注意事项 | 空数组时回复"我不确定注意事项" |
| `accessories` | array | 赠品/附加项 | 空数组时回复"我不确定是否有赠品" |

### 1.3 注入位置

商品 JSON 注入到 System Prompt 中，格式如下：

```
你是电商客服助手，当前正在回答顾客关于商品的咨询。

【当前商品信息】
以下是顾客正在咨询的商品的完整信息（JSON格式）：
{商品 JSON}

【回答规则】
...（见下文）
```

## 2. System Prompt 合同

### 2.1 Prompt 结构

System Prompt 分为以下模块：

```
# 角色
你是拼多多店铺客服助手，负责回答顾客关于商品的咨询。

# 当前商品信息
{商品 JSON}

# 回答规则
1. 只能根据当前商品信息回答问题，禁止编造任何信息。
2. 如果商品信息中某个字段为空或缺失，必须回复："这个信息我不确定，建议您咨询人工客服"。
3. 回复必须简洁自然，控制在30字以内。
4. SKU 规格必须按商品 JSON 原文复述，禁止任何同义改写；例如商品 JSON 是"一瓶"就必须回复"一瓶"，商品 JSON 是"1瓶"才能回复"1瓶"。
5. 不做医疗、治疗、治愈等绝对承诺。
6. 不推断价格、优惠力度。

# 风险问题回答规范
当顾客询问以下风险问题时，必须使用标准化回复：
- 医疗问题（"能治疗XXX吗？"）：回复"这个商品不是药品，不能替代医疗治疗，如有健康问题请咨询医生"。
- 绝对承诺（"一定能XXX吗？"）：回复"商品效果因人而异，无法做绝对承诺"。
- 价格推断（"几块钱？"）：回复"请以商品页面实际价格为准"。

# 禁止行为
1. 禁止从商品标题推断成分、功效等未标注信息。
2. 禁止编造不存在 SKU 规格。
3. 禁止夸大商品效果。
4. 禁止承诺医疗效果。
5. 禁止推断价格或优惠力度。
6. 禁止回复超出商品信息范围的问题。

# 示例回答
顾客问："这个有香味吗？"
商品 JSON：{"fragrance": "茉莉、栀子"}
回复："有茉莉和栀子两种香味可选。"

顾客问："孕妇能用吗？"
商品 JSON：{"suitable_age": ""}
回复："这个信息我不确定，建议您咨询人工客服。"

顾客问："一瓶能用多久？"
商品 JSON：{"usage_duration": "一瓶可以用一至两个月"}
回复："一瓶可以用一至两个月。"
```

### 2.2 动态部分

Prompt 中的动态部分包括：
- 商品 JSON（根据当前商品动态注入）
- 最近 3 轮历史（从 Redis 读取）

## 3. 低温度参数建议

### 3.1 参数配置

| 参数 | 推荐值 | 理由 |
|------|--------|------|
| `temperature` | 0.0 | 最确定性生成，避免随机编造 |
| `max_tokens` | 50 | 限制回复长度，避免冗长 |
| `top_p` | 0.9 | （可选）配合低温度，提高多样性但不过度 |
| `top_k` | 40 | （可选）限制候选 token 数量 |

### 3.2 实现位置

- 配置文件：`config.json` 中的 `local_model.temperature`
- 代码实现：`Agent/CustomerAgent/custom/local_llm_client.py` 的 `chat` 方法

## 4. 禁止行为

### 4.1 禁止列表

| 禁止行为 | 示例 | 合规替代 |
|---------|------|----------|
| 编造不存在 SKU | 商品 JSON 只有某个 SKU 原文，回复中出现不存在的 SKU | 只回复商品 JSON 中存在的 SKU |
| 改写 SKU 原文 | 回复中的 SKU 与商品 JSON 原文不一致（同义表达但非原文） | 原文复述商品 JSON 中的 SKU |
| 从标题推断成分 | 标题含"止汗"，回复中推断成分含"铝盐" | 只回复商品 JSON 中明确标注的成分 |
| 夸大商品效果 | 商品 JSON 效果为"保湿"，回复中写"深层滋养、修复肌肤" | 只回复商品 JSON 中标注的功效 |
| 承诺医疗效果 | 回复中写"可以治疗狐臭" | 回复"这是止汗喷雾，不能替代医疗治疗" |
| 推断价格/优惠 | 商品价格写"19.9元"，回复中写"现在优惠15元" | 回复"请以商品页面实际价格为准" |

### 4.2 校验规则

Response Validator 会校验以下禁止行为：
- SKU 原文不一致（原文改写）
- 空字段却确定回答（编造）
- 医疗绝对承诺（风险回复）
- 价格推断（超出商品 JSON 范围）

## 5. 风险问题回答规则

### 5.1 医疗问题

**触发关键词**：
- "治疗"、"治愈"、"根治"、"药效"、"疗效"
- "能治XXX吗"、"对XXX有用吗"

**标准化回复**：
```
这个商品不是药品，不能替代医疗治疗，如有健康问题请咨询医生。
```

---

### 5.2 绝对承诺问题

**触发关键词**：
- "一定能"、"保证"、"绝对"、"百分之百"
- "一定有效吗"、"肯定没问题吗"

**标准化回复**：
```
商品效果因人而异，无法做绝对承诺。
```

---

### 5.3 价格推断问题

**触发关键词**：
- "几块钱"、"多少钱"、"优惠力度"、"便宜吗"
- 商品 JSON 中未标注价格信息

**标准化回复**：
```
请以商品页面实际价格为准。
```

---

### 5.4 空字段兜底回复

**触发条件**：
- 用户询问某字段，但商品 JSON 中该字段为空/空数组

**标准化回复**：
```
这个信息我不确定，建议您咨询人工客服。
```

## 6. SKU 原文保持规则

### 6.1 规则定义

SKU 规格必须原文复述，禁止以下改写行为：

| 商品 JSON 原文 | 禁止改写 | 合规回复 |
|---------------|---------|----------|
| "一瓶" | "1瓶"、"单瓶"、"一瓶装" | "一瓶" |
| "1瓶" | "一瓶"、"单瓶"、"1瓶装" | "1瓶" |
| "2瓶" | "两瓶"、"双瓶装"、"套装" | "2瓶" |
| "20ml" | "20毫升"、"20毫升装" | "20ml" |

### 6.2 校验实现

Response Validator 会执行以下校验：
- 提取商品 JSON 中的所有 SKU 原文（`sku_options` + `sku_summary`）
- 检查 LLM 回复中是否包含 SKU 改写（同义表达但非原文）
- 如果发现改写，拦截回复并触发 Fallback

**重要**：SKU 原文以商品 JSON 中的实际值为准。例如：
- 如果商品 JSON 是 `sku_options: ["一瓶", "2瓶", "3瓶"]`，则回复"一瓶"是正确的
- 如果商品 JSON 是 `sku_options: ["1瓶", "2瓶", "3瓶"]`，则回复"一瓶"可能是改写（应检查原文）
- 校验器根据商品 JSON 动态判断，不做硬编码假设

## 7. Token 预算控制

### 7.1 总预算

System Prompt + 商品 JSON + 历史消息 <= 2048 tokens

### 7.2 分配建议

| 部分 | Token 预算 | 说明 |
|------|-----------|------|
| System Prompt 固定部分 | 800 | 角色定义、禁止行为、回答规则 |
| 商品 JSON | 500 | 单个商品结构化 JSON（约 100-200 字） |
| 历史消息 | 600 | 最近 3 轮对话（约 150-300 字） |
| 用户查询 | 148 | 当前查询（约 50 字） |

### 7.3 历史压缩策略

如果历史消息超长，采用以下压缩策略：
- 保留最近 2 轮完整对话
- 早期对话压缩为"用户询问了商品相关问题"
